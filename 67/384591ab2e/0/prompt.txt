# Task: Kuchup — Split Applications into Paginated Application States

## Context

We recently introduced the **Applications / Queue** area in the left navigation.

The current Applications experience has two main sections:

- **Apply** — positions the user still needs to apply to.
- **Applied** — positions the user has already applied to.

There are currently two important architectural problems.

### Problem 1 — Everything is loaded together

The Applications page currently loads the data for multiple tabs together instead of treating each tab as an independent data source.

For example, a user may currently have:

```text
Apply:    105 positions
Applied:   86 positions
```

The system should **not load all 191 positions when the user opens the Applications page**.

The UI should not fetch the full dataset simply to render the tabs.

The number of positions and the actual position records are two different concerns.

### Problem 2 — Applied and Rejected are mixed

The current `Applied` section also contains applications that have already received a rejection.

That means the user cannot distinguish:

```text
Applied
    ├── Waiting for response
    └── Rejected
```

This is not a meaningful application state model.

The desired state is:

```text
Apply
    → Positions still requiring application

Applied
    → User applied
    → No rejection received yet / application still active

Rejected
    → User applied
    → Application received a rejection
```

These should be separate tabs/states.

---

# Goal

Refactor the Applications area so that:

1. **Each application state is independently loaded.**
2. **Counts are independent from position-list APIs.**
3. **No application tab loads its entire dataset.**
4. **Every position list is paginated.**
5. **Apply, Applied, and Rejected are separate states.**
6. **The user only loads the actual positions for the tab they are viewing.**
7. **Opening Applications does not trigger large queries for every tab.**

The end result should be a scalable application-tracking system rather than a page that loads the user's entire application history.

---

# Required state model

The Applications area should expose at least these three states:

```text
┌─────────────┐
│ Apply       │
│ 105          │
└─────────────┘

┌─────────────┐
│ Applied     │
│ 86           │
└─────────────┘

┌─────────────┐
│ Rejected    │
│ 21           │
└─────────────┘
```

The exact UI/count presentation should follow the existing design system.

The important part is that these are **distinct application states**, not different frontend filters over one giant dataset.

---

# Important investigation

Before implementing, inspect the existing Applications implementation and determine:

1. How Applications currently retrieves queued positions.
2. How Applied positions are currently retrieved.
3. How rejected applications are represented in the database/domain model.
4. Whether application status already exists as a first-class field.
5. Whether the current API returns Apply + Applied together.
6. Whether the backend currently performs one large query.
7. Whether counts are currently calculated by fetching full records.
8. How pagination is currently implemented elsewhere in the application.
9. Whether there are existing pagination primitives/components that should be reused.
10. How the existing Panel position UI is reused by Applications.
11. Whether Apply / Applied / Rejected can be represented by the existing application lifecycle without introducing another state model.

**Do not assume a database redesign is necessary.**

First understand the existing application/queue model and make the smallest architectural change that gives us independent state queries and proper pagination.

---

# API architecture

The count and list APIs should be separate concerns.

## Count API

A lightweight count API should return counts without loading all positions.

Conceptually:

```text
GET /applications/counts
```

Response could be conceptually:

```json
{
  "apply": 105,
  "applied": 86,
  "rejected": 21
}
```

The exact endpoint and response shape should follow the existing API conventions.

The important requirement is:

> **Counting applications must not require fetching the application records themselves.**

The count query should be optimized as a count/query operation.

---

# Position list APIs

The actual positions should be loaded through separate paginated APIs.

Conceptually:

```text
GET /applications/apply
GET /applications/applied
GET /applications/rejected
```

Each endpoint must support pagination.

For example:

```text
?page=1&page_size=20
```

or whatever pagination convention the existing backend uses.

The exact URL structure is not prescribed.

The important architectural requirement is:

> **Apply, Applied, and Rejected must be independently queryable and independently paginated.**

Do not create one endpoint that loads all application states and then filters them in the frontend.

---

# Pagination

No application state should full-load its entire dataset.

For example, if the user has:

```text
Apply: 105
Applied: 86
Rejected: 21
```

opening Applications must never cause:

```text
105 + 86 + 21 = 212 position records
```

to be retrieved.

Instead:

```text
Applications opened
        ↓
optional lightweight counts request
        ↓
Show tabs
        ↓
User clicks Apply
        ↓
Fetch first 10–20 Apply positions
        ↓
User requests more
        ↓
Fetch next page
```

Use a reasonable page size consistent with the existing application.

**10–20 positions per request is the intended range; do not exceed 20 without a concrete reason.**

The implementation should support the existing project's preferred pagination mechanism, whether that is:

- page/page_size,
- cursor pagination,
- offset/limit,
- or another established mechanism.

Prefer cursor pagination if the existing architecture supports it naturally and the dataset can change while the user is browsing.

Do not introduce a new pagination mechanism unnecessarily.

---

# Lazy loading behavior

There are two acceptable UX approaches.

## Option A — Show counts immediately

When the Applications page opens:

```text
Applications

Apply       105
Applied      86
Rejected     21
```

Only the lightweight count operation runs.

Then:

```text
User clicks Apply
        ↓
Apply list API called
        ↓
First page loaded
```

Clicking Applied:

```text
User clicks Applied
        ↓
Applied list API called
        ↓
First page loaded
```

And similarly for Rejected.

This is preferred if the count query is cheap and the existing UX benefits from showing counts.

---

## Option B — Completely lazy

Alternatively, opening Applications can show:

```text
Apply
Applied
Rejected
```

without counts.

When the user clicks a tab:

```text
Tab clicked
    ↓
Count requested
    +
First paginated page requested
```

This is also acceptable if it significantly simplifies the implementation or avoids unnecessary requests.

---

## Important

Regardless of which UX option is chosen:

**Never fetch the full list merely to calculate the count.**

And:

**Never load the lists for all three tabs just because the Applications page opened.**

# Applied vs Rejected

This is a core requirement.

The backend/domain layer must distinguish:

### Apply

Position is still waiting for the user to apply.

```text
queued
→ not yet applied
```

### Applied

User has applied and there is **no rejection state**.

Conceptually:

```text
applied
→ waiting / active application
```

### Rejected

User applied and the application has received a rejection.

```text
applied
→ rejected
```

The exact underlying statuses should be determined from the existing domain model.

Do not blindly add string comparisons in the frontend.

The backend should provide the correct state.

---

# Example

Suppose the user has:

```text
105 positions waiting to apply

86 applications already submitted

17 of those are still awaiting response

69 have been rejected
```

The UI should represent the states according to the application's actual domain semantics.

For example:

```text
Apply       105
Applied      17
Rejected     69
```

Not:

```text
Apply       105
Applied      86
```

where the 69 rejected applications are incorrectly mixed into Applied.

The numbers above are only illustrative; derive the actual counts from the database.

# Backend requirements

Investigate query performance carefully.

The new APIs should query only the relevant state.

Avoid patterns such as:

```text
SELECT all applications
        ↓
load all positions
        ↓
filter in application code
        ↓
count
```

Prefer database-level filtering and counting:

```text
COUNT(...)
WHERE user_id = ?
AND state = ?
```

and:

```text
SELECT ...
WHERE user_id = ?
AND state = ?
ORDER BY ...
LIMIT ?
```

The exact query implementation should follow the existing repository/database architecture.

If indexes are needed for the new state-specific queries, add them only when justified by the existing schema/query patterns.

- Pagination state.


The user should be able to switch between tabs without losing already-loaded pages unless the existing cache strategy intentionally invalidates them.

# Important edge cases

### Position transitions

If a position changes:

```text
Apply → Applied
```

the Apply count/list must reflect it.

If:

```text
Applied → Rejected
```

the Applied and Rejected states must update correctly.

### Pagination after mutation

If the user applies to an item from the Apply tab:

- Remove/update it from the current Apply list.
- Update the relevant count.
- Do not create duplicate entries.
- The item should appear in Applied only when the application's state actually changes to Applied.

### Rejection

If an application becomes rejected:

- It should no longer be represented as active Applied.
- It should appear in Rejected.
- Counts should reflect the transition.

### Empty page

If the last item on a page moves to another state:

```text
page 3 → now empty
```

handle pagination gracefully rather than showing stale content.

### Concurrent updates

If application status changes externally while the user is browsing:

- Do not assume the frontend's old state is authoritative.
- Use the existing invalidation/refetch mechanism where appropriate.

Your review matched real deploy blockers. I pushed fixes on `cursor/go-http-fetch-scheduler-50bf` (commit `3799bdb`; PR #53 body updated). Git push from this VM failed on auth—the commit is local here; sync the branch if the remote is behind.

### Wedged `running` runs (`runCountry`)

- After `CreateFetchRun`, a **`defer`** calls **`FailRun`** unless **`FinalizeRun`** completes successfully.
- Work-row insert, progress update, or any **result-row insert** failure returns an error → run is **`failed`**, not left **`running`**.
- **`FinalizeRun`** runs only when there were no fatal DB errors in the pool phase (scrape failures still become `error` results and do not wedge the run).

### Startup / reap

- Removed **“fail every `running` row on boot”** behavior.
- **`ReapStaleRunningRuns`** only fails runs whose `started_at` is older than **`FETCH_COUNTRY_TIMEOUT_SECONDS`** (default **2700s**), so a panel company fetch in progress is not killed on worker restart.
- **`EnsureSchema`** in Go creates **`fetch_http_work`** / **`fetch_http_results`** idempotently so the first cycle does not depend on Python having migrated first.

### Deploy / double scheduler

- **Merge consumer** starts **before** the Go worker (panel entrypoint still runs `init_db`).
- **`scripts/fetch_scheduler_worker.py`** exits with code **1** for `FETCH_WORKER_KIND=http` unless **`FETCH_ALLOW_PYTHON_HTTP_SCHEDULER=1`** (test in `tests/scripts/test_fetch_scheduler_worker.py`).

### Smaller item you noted

- **`result_line`** on success is now **`HTTP fetch complete for N companies (merge pending)`** so “done” vs catalog lag is explicit in the run row.

Still not in CI: full **`--once`** subprocess test (`GO_FETCH_INTEGRATION=1`). Workday / SmartRecruiters / Bol pagination inside one company remains sequential (pool slot released between HTTP calls).

I would still treat **merge lag vs panel “finished”** as a product/ops nuance until you want run status tied to merge completion—that would be a separate contract change.
